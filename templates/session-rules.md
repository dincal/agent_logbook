# logbook 작업 규칙 (플러그인 v{version})

아래 규칙은 logbook 플러그인이 세션을 시작할 때마다 넣는다. 저장소에 커밋된 파일이 아니므로 규칙을 바꾸려면 플러그인을 고친다. logbook을 쓰는 표시는 이 기기의 `.logbook/config.json`이고, 새로 clone한 저장소에서는 `/rulebook`으로 만든다.

개발 요청은 요청 방식(직접 요청, 플랜 모드)과 상관없이 이 흐름을 따른다.

- **흐름이 달라지는 부분은 묻는다.** 코드와 자료를 먼저 조사한 뒤에도 요청에서 정해지지 않은 부분 중, 사용 흐름이 달라지는 것(어떤 명령이 무엇을 하는지, 어떤 단계를 거치는지, 언제 무엇을 승인하는지, 파일과 데이터가 어떻게 되는지)은 임의로 정하지 않고 묻는다. 질문은 한 번에 1~4개, 선택지와 권장안을 함께 준다. 사소한 것은 묻지 않고 정한 뒤 그렇게 표시한다.
- **비합리적인 결정은 알린다.** 사람의 답이나 지시가 조사한 근거, 비용, 위험, 본인이 밝힌 목표와 어긋나 보이면, 따르기 전에 한 번 무엇이 왜 걱정인지와 더 나은 안을 짧게 알린다. 그대로 가겠다고 하면 따르고, 계획 문서와 PR 본문의 주요 결정에 알린 우려로 남긴다. 취향의 문제나 근거가 약한 걱정은 알리지 않는다.
- **의견을 묻는 말에는 토론으로 답한다.** 사람이 할 일을 시키지 않고 아이디어나 의견을 물으면("이런 기능 어때?") 이슈와 브랜치를 만들지 않고 파일도 고치지 않은 채 `/discuss` 스킬을 불러 그 절차대로 토론한다. 애매하면 어느 쪽인지 한 줄로 묻는다. 결론이 나면 `/brief`로 넘기기, backlog 이슈로 남기기, 남기지 않기 중 하나를 고르게 한다.
- **이슈는 남길 일에만 만든다.** 다른 개발자가 알아야 하거나 꼭 남겨야 하는 작업(기능, 버그 수정, 설계 변경, 나중에 할 일. 한 문장으로 설명되는 작은 수정은 뺀다)은 트래커에 카드가 없으면 만들고 `<type>/<번호>-<slug>` 브랜치에서 일한다. 저장소를 고치지 않는 로컬 작업(도구 설치, 로컬 서비스 정지, 이 기기의 설정 파일)은 이슈, 브랜치, PR 없이 하고 채팅으로 보고한다. 다른 개발자도 같은 준비를 해야 하면 그 내용만 `docs/system/stack.md`에 남긴다. 다른 작업에 따라오는 문서 갱신(방금 한 로컬 작업의 반영 같은 것)은 관련 작업의 PR에 얹는다. 열린 관련 브랜치가 있으면 거기에 커밋하고, 곧 할 관련 이슈가 있으면 그 이슈에 할 일을 댓글로 남기고 그 작업에서 하며, 둘 다 없으면 이슈 없는 PR로 연다. 이슈 없는 PR은 `<type>/<slug>` 브랜치에서 연다. 이슈로 만들지 애매하면 작업 전에 한 줄로 묻는다. 기본 브랜치에 직접 커밋하지 않는다.
- **구현 전 브리핑, 구현 후 디브리핑.** 구현 전에 `/brief`로 계획 문서(원래 checkout의 `.logbook/plans/<번호>-<slug>.md`. git이 무시하므로 커밋하지 않는다)와 브리핑 HTML을 만들어 이슈에 링크하고 승인을 받는다. 결정 이유(사용자가 정한 것과 버린 대안, 알린 우려)는 PR 본문에 남긴다. PR을 연 뒤 `/debrief`로 검증 증거, 독립 리뷰 결과, 결과 HTML을 PR과 이슈에 링크하고, CHANGELOG에 이슈와 PR을 링크한 한 줄을 남긴다. 플랜 모드에서는 플랜 승인이 브리핑 승인을 대신한다. 승인한 뒤에는 다시 승인을 묻지 않고 PR과 디브리핑까지 끝낸다. 브리핑과 디브리핑은 상사에게 보고하듯 결론과 요청부터 쓴다. 그림으로 표현할 수 있는 것은 그림으로 표현하되, ERD와 흐름도는 억지로 그리지 않는다. 주요 로직의 흐름과 DB 스키마 변화는 반드시 넣는다.
- **에픽은 에픽 브랜치에서.** 여러 단계로 나뉜 긴 작업은 `/brief`가 `epic` 라벨 이슈와 단계 이슈로 계획하고 `epic/<번호>-<slug>` 브랜치를 만든다. 단계는 꼭 나눠야 할 때만, 유저 스토리가 명확히 갈리는 곳에서 크게 나눈다. 같은 스토리의 토대 작업(스키마, 공통 모듈)과 기능은 한 단계에 두고, 스토리가 하나뿐이면 크더라도 이슈 하나로 계획해 그 안에서 트랙을 나눈다. 승인한 뒤에는 세션이 단계 사이에서 멈추지 않고 단계를 표 순서대로 하나씩 진행한다. 단계 PR은 에픽 브랜치를 향하고, `/debrief`의 증거와 리뷰를 거쳐 완료 조건이 모두 ✅이고 확인된 심각한 지적이 없을 때만 에이전트가 squash로 합친 뒤 단계 이슈를 `status:done`으로 옮긴다. 그렇지 않으면 멈춘다. 단계는 결과 HTML 없이 PR 본문에 증거를 남기고, 마지막 에픽 PR에서 에픽 리뷰와 결과 보고를 한 번 한 뒤 사람이 고르면 기본 브랜치에 일반 머지(막혀 있으면 squash)한다.
- **작업 폴더는 원래 checkout이다.** 이슈와 에픽은 원래 checkout(git worktree가 아닌 처음 clone한 폴더)에서 브랜치만 바꿔 진행한다. 에픽을 시작한다고 git worktree(한 저장소를 여러 폴더에 동시에 checkout하는 git 기능)를 만들지 않는다. 원래 checkout을 쓰면 안 될 이유가 보이면(커밋하지 않은 변경, 그 폴더에서 돌아가는 서비스, 다른 세션이 그 폴더에서 작업 중인 흔적) worktree를 만들기 전에 이유를 들어 묻고, 사람이 고른 대로 worktree를 만들거나 원래 checkout에서 하거나 멈춘다. 사람이 worktree를 쓰라고 하면 따른다. 병렬 개발용 worktree는 아래 "독립 트랙은 나눠서 동시에 만든다"를 따른다. worktree는 `{plugin_root}/scripts/worktree.sh`로 원래 checkout의 `.logbook/worktrees/`에 만들고 지운다(경로는 `worktree.sh path <브랜치>`가 알려 준다).
- **독립 트랙은 나눠서 동시에 만든다.** 병렬로 할지, 어떤 방식으로 할지는 승인된 스펙을 빠르고 정확하게 끝내기 위해 구현할 때 에이전트가 정한다. 사람에게 묻거나 브리핑에 적지 않고, 시작할 때 채팅에 한 줄로 알린다. 한 이슈나 단계 안에 파일이 겹치지 않고 서로의 결과를 기다리지 않는 규모 있는 트랙이 둘 이상이면 나누는 것이 기본이다. 공통 부분(타입, 인터페이스, 설정)을 먼저 만들어 커밋한 뒤 트랙을 builder 에이전트에 동시에 맡긴다. 규모는 있지만 정형화된 트랙은 `logbook:builder-fast`(Sonnet), 범위가 분명한 기능은 `logbook:builder`(세션 모델, medium), 까다로운 알고리즘이나 동시성, 예외가 많은 수정은 `logbook:builder-deep`(세션 모델, xhigh)에 맡긴다. 한 줄로 이어진 작업, 몇 번 만에 끝나는 일, 설계 결정, 원인을 모르는 버그, 사람에게 물어야 할 수 있는 일은 나누지 않고 세션이 직접 하며, 나누지 않을 때는 시작할 때 채팅에 그 이유를 한 줄 적는다. 트랙은 같은 폴더에서 돌리거나 트랙마다 worktree를 준다. 같은 폴더의 트랙은 다른 트랙이 쓰는 중이라 확인 명령을 그 트랙의 파일로 좁히고 커밋하지 않는다. 트랙마다 전체 빌드나 전체 테스트가 필요할 때는 `worktree.sh add <브랜치> <기준 브랜치>`로 트랙마다 worktree를 만들어 경로를 넘긴다. 그 트랙은 worktree 안에서 전체 테스트를 돌리고 자기 브랜치에 커밋한다. Claude Code의 `isolation: worktree`는 기본 브랜치에서 worktree를 만들어 공통 부분이 빠지므로 쓰지 않는다. 맡긴 트랙이 확인에서 실패하거나 질문을 들고 멈추면 다시 맡기지 않고 세션이 이어받는다. 합친 뒤 전체 테스트와 커밋은 세션이 하고, 합친 트랙의 worktree와 트랙 브랜치는 원래 checkout에서 `worktree.sh remove <브랜치> --delete-branch`로 바로 지운다. 세션이 이어받은 트랙도 합친 뒤 같이 지운다. 커밋하지 않은 변경이나 합치지 않은 커밋이 남아 지우지 못하면(종료 코드 3, 4) 강제로 지우지 않고 멈춰 경로를 보고한다. 트랙과 조사는 서브에이전트나 Workflow(여러 에이전트를 스크립트로 띄우는 Claude Code 도구)로 띄운다. Workflow는 쓸 수 있는 환경에서 트랙, 조사 영역, 나눠 보는 리뷰의 리뷰어가 셋 이상이거나 끊겨도 이어 받아야 하는 긴 작업일 때 고르고, 어느 쪽이든 트랙마다 같은 builder 등급과 모델을 지정한다. Workflow를 쓸 수 없으면 서브에이전트로, 이 에이전트도 없는 하네스에서는 세션이 직접 구현한다.
- **읽기 쉽게 쓴다.** logbook으로 쓰는 모든 글(슬라이드, 계획 문서, 프로젝트 문서, 이슈와 PR)은 컴퓨터공학 학부를 졸업했지만 이 프로젝트는 모르는 사람이 막힘 없이 읽을 수 있게 쓴다. 이 프로젝트나 도구에서만 쓰는 말은 처음 나올 때 풀어 쓴다. md 파일에는 HTML을 넣지 않고 그림은 mermaid로 그린다. AI 모델을 부르는 단계는 어떤 모델에 무엇을 넣어 무엇을 시키고 무엇을 받는지 그림과 글로 자세히 적는다.
- **문서는 AGENTS.md의 문서 규칙을 따른다.** 문서의 종류와 위치, 코드와 함께 고치는 약속은 프로젝트 AGENTS.md의 문서 규칙 문단(문서와 위치 표)을 따른다. logbook 규칙과 스킬에 나오는 `docs/system/`(지금 시스템), `CHANGELOG.md`(변경 이력), `docs/manual/`(사용 설명서)은 기본 위치이고, 표가 있으면 표가 정한 위치를 뜻한다. 계획 문서와 시안 사본은 작업용 문서라 저장소에 두지 않고 원래 checkout(git worktree가 아닌 처음 clone한 폴더)의 `.logbook/`에 둔다. 지금 시스템 문서는 시스템의 지도이므로 조사는 여기서 시작한다. 표가 없거나, 지금 시스템 문서가 없거나 코드보다 뒤처졌으면 `/sync`를 권한다.
- **화면이 바뀌면 시안부터.** 화면을 새로 만들거나 눈에 띄게 바꾸는 변경은 구현 전에 시안(Claude Code에서는 `/design` 캔버스)으로 승인을 받는다. 승인본의 사본은 원래 checkout의 `.logbook/designs/<번호>-<slug>/`에 두고, 캔버스 링크를 PR 본문에 남긴다.
- **리뷰는 한 번, 고친 게 동작을 바꾸면 한 번 더.** 새 컨텍스트의 리뷰어가 PR을 본다. builder 트랙으로 만들었거나 diff가 큰 PR은 영역마다 리뷰어를 두고, 영역이 만나는 지점을 보는 리뷰어를 하나 더 둔다. 에픽 PR은 나누지 않고 에픽 리뷰를 한다. 리뷰 뒤 고친 내용이 동작을 바꾸면 고친 부분만 한 번 더 보고, 그 뒤에 남은 지적은 사람에게 넘긴다.
- **끝나면 고르게 한다.** 디브리핑 뒤 재리뷰가 필요한지 판정하고, 머지·재리뷰·남은 지적 고치기·PR 열어두기 중 권장안 하나를 이유와 함께 제시한 뒤 사람이 고른 대로 진행한다. 에픽 단계 PR은 예외로, 조건을 채우면 에이전트가 에픽 브랜치에 합친다.
- **작은 수정은 가볍게.** 한 문장으로 설명되는 수정은 이슈와 브리핑 HTML 없이 PR만 남긴다.
- **증거로 끝낸다.** 수용 기준마다 실행한 명령과 출력을 남긴다. 증거가 없는 완료 보고는 하지 않는다.
- **사람에게 넘기는 판단:** 되돌리기 어려운 결정(스키마, 공개 API, 데이터 삭제, 비용), 제품 방향, 범위 변경.
