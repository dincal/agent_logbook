# 주요 흐름

## 흐름 목록

프로젝트마다 한 번 `/rulebook`으로 규칙을 설치한 뒤에는, 모든 변경이 브리핑과 결과 보고를 거치고 프로젝트 문서는 `/sync`로 코드와 맞춥니다.

| 흐름 | 한 줄 설명 |
|---|---|
| 구현 전 브리핑 | 조사하고, 흐름이 달라지는 선택은 묻고, 계획을 승인받습니다 |
| 화면 시안 승인 | 화면이 바뀌면 구현 전에 시안을 승인받습니다 |
| 구현 후 결과 보고 | 증거, 문서 대조, 별도 리뷰를 거쳐 머지를 고릅니다 |
| 문서 동기화 | 옛 흔적을 정리하고 프로젝트 문서를 코드에 맞춥니다 |

## 구현 전 브리핑

요청이 들어오면 조사하고, 사용 흐름이 달라지는 선택은 사용자에게 묻고, 계획을 슬라이드로 보고해 착수 승인을 받습니다.

```mermaid
flowchart LR
  A["요청"] --> B["이슈와 브랜치"]
  B -->|"조사할 영역과 질문"| C{{"`**Explore 조사 에이전트**
  프로젝트 문서부터 읽고, 코드에서 근거를 찾아 보고해 달라`"}}
  C -->|"file:line 근거가 달린 보고"| D{"흐름이 달라지는 선택이 남았나"}
  D -->|"예"| Q["사람에게 질문"]
  Q --> C
  D -->|"아니오"| E["계획 문서와 브리핑 게시"]
  E --> F{"사람: 착수 승인"}
  F -->|"진행"| G["구현"]
  F -->|"수정"| E
```

- 들어오는 길은 세 가지이고 승인 방법이 다릅니다. 직접 요청은 "진행" 답변, 플랜 모드는 플랜 승인, `/mission`은 출력된 `/goal` 문장의 실행이 승인입니다.
- 플랜 모드에서는 hook이 브리핑 블록이 없거나 HTML이 든 플랜을 되돌려 보내고, 문제가 없으면 브라우저로 미리 보여 줍니다.
- 시작점: `skills/brief/SKILL.md`, `skills/mission/SKILL.md`, `hooks/plan-preview.sh`

## 화면 시안 승인

화면을 새로 만들거나 크게 바꾸는 변경은, 계획을 쓰기 전에 시안을 만들어 승인받고 그 사본을 따라 구현합니다.

```mermaid
flowchart LR
  A["캔버스에 화면 그리기"] --> B{"사람: 검토"}
  B -->|"고쳐 달라"| A
  B -->|"승인"| C["사본을 docs/designs/에 저장"]
  C --> D["사본을 따라 구현"]
```

- Claude Code에서는 `/design`과 같은 Design 캔버스를 쓰고, 캔버스를 쓸 수 없는 곳에서는 HTML 파일로 시안을 만듭니다.
- 플랜 모드와 `/mission`은 읽기 전용 단계라 시안을 올릴 수 없어서, 계획을 승인받은 뒤에 시안을 만듭니다.
- 시작점: `skills/brief/SKILL.md`의 시안 단계

## 구현 후 결과 보고

PR을 열면 완료 조건마다 증거를 모으고, 프로젝트 문서를 코드와 대조하고, 별도 리뷰어의 검토를 거친 뒤 사람이 다음 단계를 고릅니다.

```mermaid
flowchart TD
  PR["PR 열림"] --> EV["완료 조건마다 증거, 문서와 코드 대조"]
  EV -->|"PR 본문과 diff"| RV{{"`**Sonnet · medium effort**
  완료 조건마다 충족 여부를 보고, 깨지는 곳과 문서 불일치를 신뢰도와 함께 모두 적어 달라`"}}
  RV -->|"지적 목록"| VF["세션이 재현해 보고 확인한 것만 고침"]
  VF --> DB["결과 보고 게시"]
  DB --> RC["권장안 하나: 머지, 재리뷰, 남은 지적 고치기, 열어 두기"]
  RC --> Q{"사람이 선택"}
  Q -->|"머지"| HB["머지하고 핸드북 다시 게시"]
```

- PR 본문에 결과 보고 표시(`<!-- logbook:debrief -->`)가 없으면, 대화를 끝낼 때 hook이 한 번 막고 `/debrief`를 실행하라고 알려 줍니다.
- 리뷰는 PR마다 한 번 하고, 리뷰 뒤 고친 내용이 동작을 바꾸면 고친 부분만 한 번 더 봅니다.
- 시작점: `skills/debrief/SKILL.md`, `agents/reviewer.md`, `hooks/debrief-gate.sh`

| 모델 호출 | 모델(설정) | 넣는 것 | 요청(프롬프트 요지) | 받는 것과 검사 | 실패하면 |
|---|---|---|---|---|---|
| 별도 리뷰 | Sonnet, medium effort(`agents/reviewer.md`) | PR 본문의 완료 조건, diff | 완료 조건마다 충족 여부, 정상 경로에서 깨지는 곳, 프로젝트 문서와 코드의 불일치, 모델 호출 설명 누락, md 안의 HTML을 찾는다. 읽기 도구만 쓴다 | 지적마다 `file:line`, 설명, 신뢰도(0~100), 확인 방법. 세션이 재현해 보고, 확인했거나 80점 이상인 것만 남긴다 | 다른 하네스에서는 세션 모델로 같은 지침을 따른다 |

## 문서 동기화

`/sync`는 기존 프로젝트에서는 옛 흔적을 정리하고 프로젝트 문서를 새로 쓰며, logbook을 쓰던 프로젝트에서는 코드보다 뒤처진 문서만 다시 씁니다.

```mermaid
flowchart LR
  A["/sync"] --> B{"규칙 블록이 있나"}
  B -->|"없음"| R["/rulebook 먼저 안내"]
  B -->|"있음"| C{"옛 흔적이나 자리 밖 문서가 있나"}
  C -->|"있음"| D["정리표로 브리핑, 사람이 승인"]
  D -->|"스택, 흐름, 데이터 세 영역"| S{{"`**Explore 조사 에이전트 3개**
  코드에서 구성, 흐름, 모든 테이블과 모델 호출을 근거와 함께 찾아 달라`"}}
  S -->|"근거가 달린 보고"| E["문서를 새로 쓰고 옛 흔적 삭제"]
  C -->|"없음"| F["뒤처진 문서만 다시 쓰기"]
  E --> G["대조, 핸드북 게시, PR"]
  F --> G
```

- 문서마다 첫 줄에 적은 코드 경로를 보고, 그 코드가 문서보다 나중에 바뀌었으면 "뒤처짐"으로 판단합니다.
- 문서에는 코드로 확인한 사실만 남깁니다. 조사 보고는 실마리이고, 세션이 문서를 쓰기 전에 코드에서 다시 확인합니다.
- 시작점: `skills/sync/SKILL.md`, `scripts/legacy_scan.py`, `scripts/system_check.py`

| 모델 호출 | 모델(설정) | 넣는 것 | 요청(프롬프트 요지) | 받는 것과 검사 | 실패하면 |
|---|---|---|---|---|---|
| 코드 조사 | Explore 에이전트(Claude Code가 모델을 정함) | 조사할 영역(스택, 흐름, 데이터)과 질문 | 코드와 설정을 읽고, 사실마다 파일 경로와 함수 이름을 근거로 달아 보고한다. 모르는 것은 모른다고 적는다 | 영역별 보고서. 세션이 문서에 옮기기 전에 코드에서 다시 확인한다 | 세션이 직접 조사한다 |
