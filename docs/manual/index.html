01 / 13요약

logbook은 에이전트가 개발을 맡고, 사람은 정해야 할 것만 정하는 개발 흐름입니다

요청이 들어오면 에이전트가 코드와 자료를 조사하고, 다른 개발자가 알아야 하거나 꼭 남길 작업이면 이슈를 만듭니다. 쓰는 방식, 도메인 규칙과 예외 상황, 득실이 있는 기술 선택처럼 사람이 정할 결정은 객관식으로 묻고, 대화를 보지 않은 점검 에이전트가 짐작한 결정을 한 번 더 걸러 냅니다. 계획은 이슈마다 그림으로 설명하는 브리핑 화면과 이슈 본문의 글로 보고하고, 채팅에서 승인받으면 /build가 PR까지 만듭니다. PR을 연 뒤에는 증거와 별도 리뷰를 담은 결과 화면으로 머지와 머지 방식을 고르게 합니다.

02 / 13설치

플러그인을 설치하고, 저장소를 clone할 때마다 /logbook:rulebook을 한 번 실행합니다

  1. claude plugin marketplace add dincal/agent_logbook
claude plugin install logbook@agent-logbook

  2. 세션을 새로 열거나 /reload-plugins를 실행해 명령과 hook을 불러옵니다.

  3. 프로젝트에서 /logbook:rulebook을 실행합니다. 바뀔 파일을 먼저 보여 주고, 승인하면 logbook을 켜는 표시 .logbook/config.json(git에서 제외), 플랜 저장 위치, 이슈 라벨 4개(status:*)를 준비합니다. 이 표시는 clone에 따라오지 않으므로, 새로 clone한 저장소에서도 한 번 실행합니다.

  4. 이어서 /logbook:sync를 실행합니다. 문서 구조가 없으면 물어서 정하고 AGENTS.md에 문서 규칙 문단을 쓴 뒤, 예전 도구의 흔적과 자리 밖의 문서를 정리하고 프로젝트 문서를 씁니다(07장).

새 버전으로 올리기 
claude plugin marketplace update agent-logbook
claude plugin update logbook@agent-logbook

갱신한 뒤 새 세션을 엽니다. 규칙은 세션마다 플러그인에서 들어가므로 프로젝트에서 할 일은 없습니다. 0.7 이전에 AGENTS.md에 규칙 블록을 넣은 프로젝트만 /logbook:rulebook을 한 번 더 실행해 블록을 문서 규칙 문단으로 옮깁니다.

Codex · 다른 하네스 
codex plugin marketplace add <저장소 로컬 경로>
codex plugin add logbook@agent-logbook

Antigravity와 OpenCode는 skills/ 아래 폴더를 스킬 경로에 링크합니다. hook이 없으므로 hooks/session-rules.sh가 출력하는 규칙을 AGENTS.md에 직접 붙여 넣습니다(README 참고).

private 저장소 마켓플레이스를 추가하는 계정에 이 저장소를 읽을 수 있는 git 인증(SSH 키 등)이 있어야 합니다.
03 / 13흐름

요청이 어디서 들어오든 같은 흐름을 탑니다

의견만 묻는 말은 이 흐름에 들어오기 전에 /discuss로 토론하고, 넘기기로 고르면 여기서부터 이어집니다.

들어오는 길브리핑 시점착수 승인
직접 요청질문과 독립 점검 뒤, 구현 전채팅에서 "진행"
/logbook:discuss에서 넘김토론 요약을 받은 /brief가 남은 질문만 묻고 점검한 뒤채팅에서 "진행"
플랜 모드플랜을 승인한 뒤 브리핑 화면을 만듦플랜 승인 뒤 채팅에서 한 번 더 "진행"

플랜 모드는 코드를 고치기 전에 계획만 세우는 Claude Code의 읽기 전용 모드입니다. 승인한 뒤에는 /build가 다시 승인을 묻지 않고 PR과 결과 보고까지 진행합니다. 요청 하나는 이슈 하나, PR 하나이고, 큰 작업도 이슈 안에서 트랙으로 나눠 만듭니다. 이슈는 다른 개발자가 알아야 하거나 꼭 남길 작업에만 만듭니다. 한 문장으로 설명되는 작은 수정은 이슈와 브리핑 없이 PR만 열고, 방금 한 로컬 작업의 반영처럼 다른 작업에 따라오는 문서 갱신은 관련 작업의 PR에 얹습니다. 저장소를 고치지 않는 로컬 작업(도구 설치, 로컬 서비스 정지)은 채팅으로만 보고합니다.

04 / 13명령

명령 여섯 개가 흐름의 각 단계를 맡습니다

/logbook:rulebook
clone마다 한 번

저장소에서 logbook을 켭니다. 다시 실행해도 바뀐 게 없으면 "변경 없음"을 출력합니다. 0.7 이전의 규칙 블록이 있으면 지우고 그 안의 문서 규칙을 AGENTS.md 문단으로 옮깁니다. 문서 구조가 없거나 기존 프로젝트면 /sync를 이어서 실행하라고 알려 줍니다.

결과
.logbook/config.json, 라벨, 플랜 저장 위치(.logbook/plans)
/logbook:discuss
스펙을 정하기 전

아이디어를 에이전트와 따져 봅니다. 에이전트는 코드와 웹을 읽기만 하며 근거를 대고, 동의하거나 자신 있게 반론합니다. 파일, 이슈, 브랜치는 건드리지 않습니다. 선택지가 있는 질문은 질문 도구로 객관식으로 묻습니다. 끝나면 요약을 보이고 /brief로 넘기기, backlog 이슈로 남기기, 남기지 않기 중 권장안과 함께 고르게 합니다. 명령 없이 의견만 물어도 같은 방식으로 답합니다.

예
/logbook:discuss 로그인에 속도 제한이 필요할까?
/logbook:brief
구현 전

조사하고, 구조·동작·기술·계약 네 관점으로 사람이 정할 결정을 찾아 객관식으로 묻습니다. 계획을 쓰기 전에 대화를 보지 않은 logbook:checker(Opus, high)가 짐작한 결정과 빠진 결정을 찾아 질문으로 돌려줍니다. 화면이 바뀌면 시안을 승인받고, 트랙 그래프를 담은 계획 문서(로컬 .logbook/plans/, 커밋하지 않음), 이슈마다 그림으로 설계한 브리핑 화면, 이슈 본문의 글 브리핑을 만든 뒤 채팅에서 승인을 묻습니다. 승인하면 /build로 넘깁니다. 중단하면 나중에 할지(이슈를 backlog로 돌리고 브랜치를 남기며, 계획 문서를 이슈 댓글로 남김) 버릴지(이슈를 닫고 브랜치 삭제)를 묻습니다. 큰 작업도 이슈 하나, PR 하나로 계획합니다.

예
/logbook:brief 로그인에 속도 제한 추가 · /logbook:brief #42
/logbook:build
브리핑 승인 직후(자동), 끊긴 작업을 이어 갈 때

계획 문서의 트랙 그래프대로 만듭니다. 묶음 0의 공통 부분을 세션이 먼저 만들고, 묶음마다 builder 트랙을 Workflow 하나로 동시에 돌립니다. 위험한 트랙은 합치기 전에 리뷰하고, 트랙마다 커밋하며, 묶음마다 전체 테스트를 돌린 뒤 PR을 열고 /debrief를 실행합니다(09장).

예
/logbook:build #42(끊긴 작업 이어 가기)
/logbook:debrief
PR 직후

완료 조건마다 증거를 모으고, 프로젝트 문서를 코드와 대조하고, 별도 리뷰어의 검토를 받은 뒤, 계획과 결과를 그림으로 비교한 결과 화면을 PR과 이슈에 링크합니다. 끝나면 머지·재리뷰·남은 지적 고치기·PR 열어두기 중 권장안을 이유와 함께 제시하고, 머지 방식(squash, merge commit)도 같은 질문에서 고르게 합니다. 트랙이 둘 이상이면 트랙별 커밋을 남기는 merge commit을 권합니다.

예
/logbook:debrief · /logbook:debrief 57
/logbook:sync
처음 도입할 때, 문서가 뒤처졌을 때

문서 구조가 AGENTS.md에 없으면 물어서 정하고 문서 규칙 문단을 씁니다. 예전 도구의 흔적과 자리 밖의 문서를 정리하고, 프로젝트 문서(기본 docs/system/)를 코드에서 쓰거나 뒤처진 부분만 다시 씁니다. 도메인 규칙이 있는 프로젝트는 처음 쓸 때와 full일 때 업무 규칙 문서(rules.md) 초안을 쓰고, 규칙마다 의도한 것인지 객관식으로 확인받습니다. logbook이 켜지지 않은 저장소면 멈추고 /rulebook을 먼저 안내합니다.

예
/logbook:sync · /logbook:sync full

Claude Code에서 리뷰어와 독립 점검(logbook:checker)은 Opus 모델에 high effort, 코드 조사는 Sonnet 모델로 돕니다. 트랙은 /brief가 계획 문서의 트랙 그래프로 정하고 사람에게 묻지 않습니다. 독립 트랙이 둘 이상이면 나눠서 builder 에이전트(builder-fast는 Sonnet, builder와 builder-deep은 세션 모델)에 맡기는 것이 기본이고, 나누지 않으면 그래프에 이유를 한 줄 남깁니다. 트랙으로 만들었거나 2,000줄 이상인 PR은 영역별 리뷰어와 영역이 만나는 곳을 보는 리뷰어가 나눠 봅니다. 트랙마다 전체 테스트가 필요하면 원래 폴더의 .logbook/worktrees/에 git worktree(한 저장소를 여러 폴더에 동시에 checkout하는 git 기능)를 만들어 맡기고, 합친 뒤 바로 지웁니다. 그 밖에는 원래 폴더에서 브랜치만 바꿔 작업하고, 원래 폴더를 쓰면 안 될 이유(커밋하지 않은 변경, 그 폴더에서 돌아가는 서비스)가 보이면 worktree를 만들기 전에 묻습니다. 다른 하네스에서는 모두 세션 모델이 직접 합니다.

05 / 13브리핑 쓰는 법

브리핑은 이슈마다 그림으로 설명하는 화면으로 만들고, 글은 채팅과 이슈 본문에 둡니다

꼭 들어갈 정보

결론과 요청, 무엇이 바뀌나, 주요 로직 흐름, 결정(사람이 정한 것과 에이전트가 정한 것), 위험과 판단 필요, 완료 조건은 모든 브리핑 화면에 들어갑니다. DB 변경과 화면 시안은 해당될 때만 넣습니다. 에이전트가 정한 것 중 동작이나 비용을 바꾸는 것은 사람이 정한 것만큼 크게 그림으로 보여 주고, 사소한 것만 짧게 모읍니다.

묻는 기준

쓰는 방식, 도메인 규칙과 예외 상황, 득실이 있는 기술 선택은 사람에게 묻습니다. 구조·동작·기술·계약 네 관점으로 빠진 결정을 찾고, 선택지를 나열할 수 있으면 질문 도구로 권장안을 먼저 두어 묻습니다. 이미 정해진 것과 사람이 신경 쓰지 않을 조정값은 에이전트가 정하고 브리핑에 표시합니다. 답이 조사 결과나 비용, 위험, 본인의 목표와 어긋나 보이면 한 번 알리고, 그대로 가겠다고 하면 따릅니다. 기준은 templates/questions.md에 있습니다.

화면과 그림
  • 정해진 틀 없이 이슈마다 설계합니다. 글은 짧은 제목과 설명만 두고, 내용은 그림으로 보여 줍니다. 기준은 templates/briefing.md에 있습니다.
  • 버튼, 토글, 움직임은 그것 없이 보여 줄 수 없을 때만 씁니다. 억지로 넣지 않습니다.
  • ERD와 흐름도는 억지로 그리지 않되, 주요 로직의 흐름과 DB 스키마 변화는 반드시 넣습니다. 프로젝트 문서의 ERD에는 DB의 모든 테이블을 넣습니다.
  • AI 모델을 부르는 단계는 모델, effort, 프롬프트 요지(넣는 것, 요청, 받는 것)를 그림에 적습니다.
  • 계획 문서와 프로젝트 문서 같은 md 파일에는 HTML을 넣지 않습니다. 그림은 mermaid로 그립니다.
글은 어디에

승인을 묻는 채팅에는 요약 한 문장, 동작이나 비용을 바꾸는 에이전트의 결정, 위험과 판단 필요, 완료 조건 수, 화면 링크를 붙입니다. 이슈 본문에는 다른 개발자가 읽을 글 브리핑을 넣습니다. 독자는 컴퓨터공학 학부를 졸업했지만 이 프로젝트는 모르는 사람이고, 기준은 templates/writing.md에 있습니다.

화면 시안 화면을 새로 만들거나 크게 바꾸면 구현 전에 Claude Code의 /design 캔버스로 시안을 만들어 승인받습니다. 승인본의 사본은 커밋하지 않고 로컬 .logbook/designs/<번호>-<slug>/에 두고, 승인된 화면은 링크만 걸지 않고 브리핑 화면 안에 넣습니다. 캔버스 링크는 PR 본문에 남습니다.
06 / 13프로젝트 문서

  • 플랜에 <!-- brief:begin --> 줄이나 끝 줄이 없으면 플랜을 되돌리고 무엇이 빠졌는지 알려 줍니다. HTML이 든 플랜도 되돌립니다. 미리보기 창은 띄우지 않습니다.
  • 승인 직후에는 코드보다 먼저 이슈와 브랜치, 계획 파일 옮기기, 화면이 바뀌면 시안 승인, 브리핑 화면과 이슈 본문의 글을 마치고 채팅에서 한 번 더 승인받으라고 알립니다. 승인하면 /build로 넘깁니다.

debrief-gate · 대화가 끝날 때

PR에 결과 보고가 없으면 한 번 막습니다

  • 기본 브랜치, PR 없음, 머지된 PR, gh 오류, 이미 확인한 커밋은 그대로 통과합니다.
  • 같은 커밋에서는 한 번만 막고, 새 커밋이 생기면 다시 한 번 막습니다.
09 / 13/build

브리핑을 승인하면 /logbook:build가 트랙 그래프대로 묶음씩 만들고 PR까지 갑니다

flowchart LR
  G["계획 문서의 트랙 그래프"] --> W0["묶음 0: 공통 부분(세션)"]
  W0 --> RV{"위험한 트랙인가"}
  WN["다음 묶음: builder 트랙을 Workflow 하나로 동시에"] --> RV
  RV -->|"예"| R["합치기 전에 리뷰어(영역 모드)"]
  RV -->|"아니오"| C["트랙마다 커밋"]
  R --> C
  C --> T["전체 테스트, 진행 기록에 체크"]
  T -->|"다음 묶음"| WN
  T -->|"끝"| PR["PR과 /debrief"]

  1. /brief가 계획 문서의 ## 상세에 트랙 그래프를 씁니다. 표 한 줄이 트랙 하나이고, 묶음, 트랙, 맡을 에이전트(builder-fast, builder, builder-deep 또는 세션), 바꿀 파일, 기다리는 트랙, 위험, 확인 명령을 적습니다. 사람에게 묻지 않고 브리핑 화면에도 넣지 않습니다.

  2. 채팅에서 "진행"을 고르면 이슈가 status:in-progress로 바뀌고 /build가 바로 시작합니다. 다시 승인을 묻지 않습니다.

  3. 묶음 0의 공통 부분(타입, 인터페이스, 설정)은 세션이 만들고, 나머지 트랙은 보통 한 묶음으로 모아 Workflow 하나로 동시에 돌립니다. 묶음은 세션이 리뷰하고 합치는 단위라서, 앞 결과를 리뷰하고 합쳐야만 뒤 트랙을 시작할 수 있을 때만 더 나눕니다. 같은 묶음의 트랙끼리는 파일이 겹치지 않습니다.

  4. 그래프에 위험으로 표시한 트랙(까다로운 로직, 다른 트랙이 기대는 계약, 예외가 많은 수정)은 묶음 0이든 다른 묶음이든 합치기 전에 리뷰어가 영역 모드로 보고, 확인된 심각한 지적을 먼저 고칩니다. 트랙마다 커밋 하나로 합치므로 merge commit으로 머지하면 트랙 하나만 되돌릴 수 있습니다.

  5. 묶음마다 전체 테스트를 돌리고 계획 문서의 진행 기록에 체크합니다. 마지막 묶음 뒤에 PR을 열고 /debrief를 실행합니다.

  • 세션이 끊겼으면 /logbook:build #<번호>를 실행합니다. 진행 기록과 브랜치를 비교해 체크되지 않은 첫 묶음부터 이어 가고, 이미 PR이 열려 있으면 /debrief로 넘깁니다.
  • 이슈가 status:in-progress가 아니면(승인받지 않은 계획) 시작하지 않고 /brief #<번호>를 안내합니다. 계획 문서가 이 기기에 없으면 계획을 세운 기기에서 이어 가거나 여기서 다시 계획하라고 알리고 멈춥니다.
  • 전체 테스트가 고칠 수 없게 실패하거나 사람에게 물을 것이 생기면 그 묶음에서 멈추고 이유를 보고한 뒤 "고친 뒤 이어서 / 중단"을 묻습니다. 중단해도 브랜치와 커밋, 계획 문서는 그대로 남습니다.
  • 그래프와 실제가 다르면(예상하지 못한 공통 파일, 생각보다 작은 트랙) 그래프를 고치고 이유를 계획 문서의 결정 기록과 PR 본문에 남깁니다.

  • 글의 모양 모든 글은 단계 아이콘과 이름을 단 큰 제목, 진행 줄(계획 → 만들기 → 확인 → 반영), 본문, 작은 바닥글로 올라옵니다. 상위 메시지의 진행 줄은 단계가 바뀔 때 저절로 고쳐집니다. 머지하거나 버려서 쓰레드가 닫히면 그 뒤의 답글은 읽히지 않는다는 안내가 상위 메시지에 붙습니다. 이전 형식으로 만든 쓰레드는 상위 메시지를 한 번 다시 쓰면 새 형식이 됩니다.
  • 글과 첨부 글은 개발 용어를 뺀 쉬운 말로 써서 기획자도 읽습니다. 개발자용 화면은 PNG(페이지 전체 높이 한 장)와 HTML로 같은 답글에 붙습니다. HTML은 Slack에서 화면으로 그려지지 않으므로 내려받아 브라우저로 엽니다. PNG를 찍으려면 Google Chrome이 필요하고, 없으면 글과 HTML만 올라옵니다. 화면이 지난 게시와 같으면 글만 올라옵니다.
  • 답글 처리 에이전트는 시안과 브리핑의 승인을 묻기 전, 묶음 끝, PR을 열기 전, 디브리핑, 머지 전에 쓰레드의 새 답글을 읽고 방향 변경, 질문, 참고로 나눠 채팅에 알립니다. 방향 변경은 반영, 무시, 나중에 중에서 사용자가 고르고, 에이전트가 직접 계획을 바꾸지 않습니다. 봇이 올린 메시지는 읽지 않고, 같은 답글을 두 번 알리지 않습니다.
  • 실패해도 멈추지 않습니다 채널이 정해지지 않았으면 아무것도 하지 않고, 토큰이 없으면 건너뛰며 한 줄로 알립니다. Slack, GitHub, Chrome 호출이 실패해도 채팅에 한 줄 알리고 다음 단계로 갑니다.
  • 한계 logbook이 직접 한 머지와 닫힘만 올라옵니다. GitHub 웹에서 머지하거나 닫은 이슈는 쓰레드에 끝이 남지 않습니다. 답글은 단계 경계에서만 읽으므로, 세션이 쉬는 동안 달린 답글은 다음 경계에서 알려 줍니다.
  • 토큰을 바꿀 때 앱 설정의 OAuth & Permissions에서 토큰을 다시 발급하거나 앱을 다시 설치하고, 팀원은 LOGBOOK_SLACK_TOKEN 값을 새 토큰으로 바꿉니다. 토큰이 유출됐다면 바로 다시 발급합니다. 봇은 초대받은 채널의 기록만 읽을 수 있습니다.
13 / 13문제 해결

자주 막히는 곳은 열 가지이고, 대부분 명령 하나로 풀립니다

규칙이 적용되지 않는 것 같습니다저장소에 .logbook/config.json이 없으면 hook이 규칙을 넣지 않습니다. 새로 clone한 저장소라면 /logbook:rulebook을 실행하고 세션을 새로 엽니다. 문서 규칙이 안 보이면 작업 폴더 위쪽에 다른 CLAUDE.md가 있어 AGENTS.md를 읽지 않는 경우이니, 프로젝트에 @AGENTS.md 한 줄짜리 CLAUDE.md가 있는지 확인합니다.
gh 명령이 다른 계정으로 실행됩니다/logbook:rulebook이 gh 계정을 .logbook/config.json에 적고, 세션 규칙의 트래커 줄로 넣습니다. 명령과 hook은 GH_TOKEN="$(gh auth token --user <계정>)"으로 그 계정을 씁니다.
/sync가 멈추고 /rulebook을 먼저 하라고 합니다logbook이 켜지지 않은 저장소입니다(.logbook/config.json 없음). /logbook:rulebook을 실행한 뒤 /logbook:sync를 다시 실행합니다.
system-check가 "뒤처짐"을 알립니다문서가 설명하는 코드가 문서보다 나중에 바뀌었습니다. 해당 절을 고치거나 /logbook:sync를 실행합니다. 확인해 보니 고칠 것이 없으면 문서 첫 줄 주석의 checked="날짜"만 고칩니다.
브리핑이나 핸드북 링크를 만들 수 없습니다Artifact는 claude.ai에 로그인하고 Anthropic API로 연결된 세션에서만 게시됩니다. 게시할 수 없으면 .logbook/의 로컬 파일 경로를 링크로 씁니다.
/design 시안을 만들 수 없습니다Claude Code 2.1.265 이상과 claude.ai 로그인이 필요합니다. 쓸 수 없는 환경에서는 .logbook/designs/에 HTML 시안을 만들어 브라우저로 확인합니다.
플랜이 계속 되돌아옵니다플랜에 <!-- brief:begin -->와 <!-- brief:end -->가 각각 단독 줄로 있는지, HTML 태그가 들어 있지 않은지 확인합니다. 작은 수정이면 <!-- brief:skip --> 한 줄만 넣습니다. 플랜 모드에서는 미리보기 창이 뜨지 않고, 승인한 뒤 브리핑 화면을 만듭니다.
/build가 시작하지 않고 멈춥니다이슈가 status:in-progress가 아니면 승인받지 않은 계획이라 멈춥니다. /logbook:brief #<번호>로 브리핑을 마칩니다. 계획 문서는 커밋하지 않으므로 다른 기기에서 세운 계획이면 그 기기에서 이어 가거나, 이슈를 status:todo로 돌리고 여기서 다시 계획합니다.
대화가 끝나지 않고 계속 돌아옵니다열린 PR 본문에 <!-- logbook:debrief -->가 있어야 통과합니다. /logbook:debrief를 실행합니다. 계획 문서가 없는 PR이면 결과 화면 없이 PR 본문에 증거와 표시를 남깁니다.
Codex에서 명령이 보이지 않습니다codex plugin list로 설치 상태를 보고 새 세션을 엽니다. hook은 /hooks에서 신뢰 등록해야 실행됩니다.
